## [1.4.2] - TBD - llama.cpp Inference and Provenance Support

## Overview

v1.4.2 adds llama.cpp `llama-server` as a selectable inference provider for Inference Operators and the Gateway embedded Operator, and a llama.cpp model store layout for the Provenance capability. Ollama remains the default provider. The llama.cpp flags are additive, and existing Ollama flags and defaults are unchanged.

## Added

- `--inference-llamacpp-endpoint` and `--inference-llamacpp-model-root` on `ztd operator start`, `ztd operator deploy`, and `ztd gw start`. The llama.cpp endpoint selects the llama.cpp provider instead of Ollama. The model root is the llama-server `--models-dir` as seen by the Operator or Gateway, and is required with the endpoint.
- `--model-storage-format ollama|llamacpp` on the same commands selects the model store layout under `--model-storage-root` for the Provenance capability. The default is `ollama`.
- Setting both an Ollama endpoint and a llama.cpp endpoint fails when inference is enabled. With llama.cpp, `--inference-keep-alive` accepts `-1` or `0`.
- `ztd gw status` lists only the inference flags for the provider an Operator serves. `ztd operator show`, `ztd operator list --json`, and the TUI Operator details show the llama.cpp endpoint, model root, and model store format.
- Sovereign formation roles accept provider class `ollama` or `llamacpp`.

## Changed

- `ztd eval models pull` requires an Inference Operator that serves Ollama. An Operator serving llama.cpp fails with `inference: Ollama model pull requires an Inference Operator serving Ollama`.
- Model inventory, residency, release, and freeze work with either provider.
- Delegated formation roles still cannot declare a local provider class. Built-in formations stay on Ollama.

## Fixed

- Decision backend kind reports the configured provider (`ollama-systemone` or `llamacpp-systemone`) rather than always `ollama-systemone`.
