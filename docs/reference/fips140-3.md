# FIPS 140-3 Module Linkage and Scope

## Purpose

Defines the FIPS 140-3 cryptographic module linkage, operational claim boundary, and runtime verification procedures for Linux AMD64 `ztd` deployments. Documents the Go Cryptographic Module version that `ztd` links at build time, the operating environment named in the repository, and the build and verification commands. `ztd` is an application that links a cryptographic module; the repository does not record a separate validation of `ztd` itself under FIPS 140-3.

## Invariants

Ids are stable. Append the next free number in a topic. Do not renumber.

### Compliance scope (`INV-FIPS-SCOPE`)

| ID | Rule |
| :--- | :--- |
| INV-FIPS-SCOPE-01 | The `ztd` FIPS 140-3 compliance claim applies only to the linux/amd64 binary built with `GOFIPS140=v1.0.0` and `CGO_ENABLED=0` (`make fips-build`, or the linux/amd64 artifact of `make build-all`), running in approved mode, on the operating environment named in [Operating environment](#operating-environment). The claim does NOT extend to other operating systems or architectures, to binaries built without `GOFIPS140`, or to processes launched with `GODEBUG=fips140=off`. |
| INV-FIPS-SCOPE-02 | A deployment is within the compliance claim only if `./ztd version --fips` reports `FIPS 140-3 mode: enabled` and `FIPS module version: v1.0.0`, and the deployed binary is the linux/amd64 artifact described in INV-FIPS-SCOPE-01. The status command reports runtime module state; it cannot show which build flags produced the binary. Confirm the artifact against its `.sha256` file written by the build. |
| INV-FIPS-SCOPE-03 | Linking a validated module does NOT automatically satisfy every regulatory mandate governing an enterprise environment. Deploying organizations remain authoritative for external key strength, secure key generation, and approved use of cryptographic services. |

### Validated module (`INV-FIPS-MODULE`)

| ID | Rule |
| :--- | :--- |
| INV-FIPS-MODULE-01 | The linked cryptographic module is Go Cryptographic Module v1.0.0 (`GOFIPS140_VERSION` in the `Makefile`). The `Makefile` and `version.go` cite it as CMVP Certificate #5247, and the `Makefile` cites CAVP Certificate A6650. The repository does not state validation dates, security level, or module classification; this document does not assert them. Check the NIST certificate page for those details. |
| INV-FIPS-MODULE-02 | This repository makes no assurance about the minimum cryptographic strength of externally supplied keys, generated passwords, or parameters derived from external inputs. Deployments MUST independently assess external key material. |

### Build configuration (`INV-FIPS-BUILD`)

| ID | Rule |
| :--- | :--- |
| INV-FIPS-BUILD-01 | `GOFIPS140=v1.0.0` is a build-time toolchain setting. `BUILD_ONE` in the `Makefile` sets it for Linux targets. At build time it links the frozen module v1.0.0 and, per the Go FIPS 140-3 guide and the `version.go` help text, makes approved mode the default. `./ztd version --fips` reports module state at runtime through `crypto/fips140` and cannot show which build flags produced the binary (`internal/cli/cmd/version/version.go`). |
| INV-FIPS-BUILD-02 | `make build-all` passes `GOFIPS140=v1.0.0` to every Linux target in `PLATFORMS` and unsets it (`env -u GOFIPS140`) for non-Linux targets (`BUILD_ONE` in the `Makefile`). This document's claim and the repository's CI checks cover only linux/amd64. `make build` does not set `GOFIPS140`; a binary built without it does not link the validated module. Production builds MUST use `make fips-build` or the linux/amd64 artifact of `make build-all`. |
| INV-FIPS-BUILD-03 | The binary MUST be built with `CGO_ENABLED=0` and verified as statically linked. `make verify-static` checks `file` and `ldd` output for the binary named by `STATIC_BINARY` (default `bin/ztd-linux-amd64`); CI sets `STATIC_BINARY=bin/ztd-fips-linux-amd64`. |

### Runtime control (`INV-FIPS-RUNTIME`)

| ID | Rule |
| :--- | :--- |
| INV-FIPS-RUNTIME-01 | `GODEBUG=fips140=off` disables approved mode at process initialization, overriding the build-time default. This setting is outside the claim in INV-FIPS-SCOPE-01 and MUST NOT be used in FIPS-regulated production environments. |
| INV-FIPS-RUNTIME-02 | `GODEBUG=fips140=only` turns on Go's enforcement mode, which rejects non-approved operations (the enforcement warning text in `internal/cli/cmd/version/version.go`). The repository uses it as a verification gate: `make fips-verify` runs under it, and the CI job invokes that target. The `version.go` help text states that CI and release gates that require the strict posture should run the binary under it, and that production runs commonly leave enforcement off because some non-approved primitives (ChaCha20-Poly1305 SSH) are required. Do not treat enforcement as a production setting without testing the workload against it. |

## Procedures

### Compliance scope

`ztd` linux/amd64 binaries built with `GOFIPS140=v1.0.0` link Go Cryptographic Module v1.0.0 and initialize into FIPS 140-3 approved mode by default. The `Makefile` cites NIST CMVP Certificate #5247 and CAVP Certificate A6650 for this module. The claim covers the use of approved cryptographic services provided by that module on the operating environment described below. It does not constitute a separate CMVP validation of the `ztd` platform binary.

To remain within the claim, all of the following MUST be true:
- The deployed binary is the linux/amd64 artifact built with `GOFIPS140=v1.0.0` and `CGO_ENABLED=0`.
- The binary runs on the operating environment named in [Operating environment](#operating-environment).
- `./ztd version --fips` reports approved mode enabled and module version `v1.0.0`.
- The deployment selects approved algorithms and key lengths for external key material (INV-FIPS-MODULE-02, INV-FIPS-SCOPE-03). `ztd version --fips` does not check this.

### Validated module

- **Module Name**: Go Cryptographic Module v1.0.0 (`GOFIPS140_VERSION` in `Makefile`)
- **CMVP Certificate**: [#5247](https://csrc.nist.gov/projects/cryptographic-module-validation-program/certificate/5247), cited in `Makefile` and `internal/cli/cmd/version/version.go`. Validity dates and level are not recorded in the repository; see the NIST page.
- **Algorithm Validation**: CAVP Certificate A6650, cited in `Makefile` comments
- **Standard**: FIPS 140-3

### Cryptographic services

When running in approved mode, `ztd` routes the cryptographic calls listed below through the linked module. Each item names the repository source that establishes the behavior. Where the repository does not establish whether an algorithm is an approved service of the validated module, this document makes no claim for it.

- **TLS**: The TLS configuration sets `MinVersion` to TLS 1.3 and `CurvePreferences` to `FIPSCurvePreferences()` (`internal/certs/embed.go`, `FIPSCurvePreferences` and its call site in the TLS configuration; `internal/services/gateway/gateway_certs.go`, TLS configuration). That list is `X25519MLKEM768`, `P-384`, and `P-256`. Standalone X25519 is not in it. Whether the hybrid `X25519MLKEM768` group is an approved service of the validated module is not established by repository sources, and this document makes no claim for it.
- **Platform PKI and Certificates**: `internal/services/gateway/gateway_certs.go` generates root CA, intermediate CA, and service keys with `ecdsa.GenerateKey(elliptic.P256(), rand.Reader)`. `SignCSR` and `SignPlatformAppCSR` check the CSR signature and reject CSRs whose public key is not P-256. The CRL template uses `x509.ECDSAWithSHA256`. Certificates whose signature algorithm is Ed25519 are rejected (`constants.ErrPKIEd25519CertRejected`).
- **Application Signatures**: Consensus votes (`internal/services/governance/l2_consensus.go`), actuator receipts and capabilities (`internal/services/governance/l5_actuator.go`, `internal/services/governance/capability.go`), platform enrollment proofs, public-feed proofs, and compliance report signatures (`internal/services/compliance/report/signing.go`) use Ed25519. Notary approvals use ECDSA P-256 with SHA-256: signed CLI approval proofs verify against an ECDSA P-256 key (`internal/governance/cli_approval.go`). Passkey assertions are verified by go-webauthn under the algorithm the authenticator registered. The repository does not establish whether Ed25519 is an approved service of the validated module, so this document makes no claim for it.
- **Symmetric Data Protection**: The vault encrypts with AES-256-GCM (`internal/services/vault/vault_crypto.go`, `KeySize = 32`, `EncryptAESGCM`; `internal/services/vault/vault.go`, `EncryptWithAAD`). The Local-First Events Store, commitment ledger, and suspended transaction store content is encrypted through `encryptEventsContent` (`internal/services/storage/local_first_events_store.go`), which returns an error when the vault is locked or absent and has no plaintext branch. The token store adapter encrypts values with `vault.EncryptWithAAD` (`internal/services/gateway/encrypted_kv_adapter.go`). Vault key derivation uses HKDF-SHA-256 (`DeriveKEK`, `DeriveSubkey` in `vault_crypto.go`). `vault.HMACSHA256` computes HMAC-SHA-256 over a DEK-derived subkey (`vault.go`).
- **Random Number Generation**: Key generation (`gateway_certs.go`) and vault nonces (`GenerateNonce`, `vault_crypto.go`) use `crypto/rand`. The repository does not specify the DRBG or its seeding. Those are properties of the Go module and are not described here.
- **Passkey WebAuthn**: `internal/services/gateway/passkey_service.go` calls `webauthn.New` without an explicit credential algorithm list. Registration uses go-webauthn's `CredentialParametersDefault()` (`vendor/github.com/go-webauthn/webauthn/webauthn/registration_credential_parameters.go`, `registration.go`), which lists ES256 (ECDSA P-256 with SHA-256) first. The ML-DSA list `CredentialParametersPQCRecommendedL3()` is build-tagged `go1.27` and is not referenced by the vendored `registration.go`. Which algorithms a given authenticator supports is not covered here.
- **SSH Operations**: Governed native SSH tools use `golang.org/x/crypto/ssh` (`go.mod`: `golang.org/x/crypto v0.58.0`). When `fips140.Enabled()` is true, the vendored package removes default ciphers that have no FIPS-mode implementation, removes host-key and public-key algorithms whose hash is not allowed, and branches its key-exchange defaults (`vendor/golang.org/x/crypto/ssh/common.go`, `cipher.go`, `kex.go`). `cipher.go` notes that AES-GCM with arbitrary IVs is not allowed under `fips140=only`, so SSH AES-GCM works under `fips140=on` but not under enforcement.

### Operating environment

- **Operating System**: Debian GNU/Linux 12 (Bookworm). A `Makefile` comment names this as the affirmed FIPS operating environment. The affirmation itself is not in the repository.
- **Architecture**: AMD64 (x86_64)
- **Compilation Environment**: for Linux targets, the `BUILD_ONE` recipe in `Makefile` runs `go build` with `GOFIPS140=v1.0.0`, `CGO_ENABLED=0`, `-trimpath`, `-tags netgo,osusergo`, and the `-ldflags` it sets. `make fips-build` runs the same flags for linux/amd64.

The repository verifies only linux/amd64. `make build-all` also sets `GOFIPS140` for the other Linux targets in `PLATFORMS`, but no repository check covers them and this document makes no claim for them. Darwin and Windows targets unset `GOFIPS140` and are outside the claim.

### Build configuration

Compilation with `GOFIPS140=v1.0.0` links the validated module and makes approved mode the default:

```bash
# Build the dedicated Linux AMD64 FIPS binary
make fips-build

# Or build all platform targets; Linux targets, including linux/amd64, are built with GOFIPS140
make build-all
```

`make fips-build` writes `bin/ztd-fips-linux-amd64`, writes its SHA-256 digest to `bin/ztd-fips-linux-amd64.sha256`, and copies the binary to the repository root as `ztd-fips`.

`make build-all` writes each target to `bin/`, writes `bin/ztd-binaries.json` and checksums through `internal/tools/ztdbinaries`, and copies the host binary to the repository root as `ztd`. The root `ztd` copy is not the `ztd-fips` artifact.

### Runtime verification

Verify the active cryptographic mode on the deployed host:

```bash
./ztd version --fips
```

The `--fips` block follows the build metadata lines and prints:
```text
FIPS 140-3 mode:     enabled
FIPS enforcement:    disabled
FIPS module version: v1.0.0
```

With `--json`, the same status is returned as a `fips140` object with `enabled`, `enforced`, and `module_version` fields.

Exit behavior (`internal/cli/cmd/version/version.go`):
- Approved mode enabled: exit `0`. If enforcement is disabled, the command also prints a warning.
- Approved mode disabled: prints remediation guidance and returns `constants.ErrFIPSModeNotActive` (non-zero exit).

### CI verification

The `CI (FIPS 140-3)` workflow (`.github/workflows/build-and-test-fips.yml`) runs on the `ubuntu-latest` runner. That runner is not the Debian GNU/Linux 12 environment named above, so the workflow does not validate that environment. The workflow runs:
1. `make fips-verify`: builds `bin/ztd-fips-linux-amd64` and runs `./ztd-fips version --fips` under `GODEBUG=fips140=only`.
2. `make verify-static STATIC_BINARY=bin/ztd-fips-linux-amd64`, which checks `file` output for "statically linked" and `ldd` output for "not a dynamic executable".

The workflow does not run the full platform unit or integration suites. See the [Testing Guide](../devs/tests.md#cross-component-test-execution) for local suite targets and the manual CI integration option.

## Anti-patterns

- Deploying binaries built with ordinary `make build` or `go install` without `GOFIPS140=v1.0.0` in FIPS-regulated environments (INV-FIPS-BUILD-02).
- Operating `ztd` with `GODEBUG=fips140=off` in FIPS environments (INV-FIPS-RUNTIME-01).
- Deploying non-linux/amd64 binaries, including Windows and macOS builds, under this document's compliance claim (INV-FIPS-SCOPE-01).
- Treating diagnostic enforcement (`GODEBUG=fips140=only`) as a production setting without testing the workload against it (INV-FIPS-RUNTIME-02).
- Failing to verify the binary status with `./ztd version --fips` during deployment audits (INV-FIPS-SCOPE-02).
