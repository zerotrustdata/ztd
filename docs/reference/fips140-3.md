# FIPS 140-3 Module Linkage and Scope

## Purpose

Defines the FIPS 140-3 cryptographic module linkage, operational claim boundary, and runtime verification procedures for Linux AMD64 `ztd` deployments. Documents the validated Go Cryptographic Module linked by `ztd`, specifies supported host operating environments, and details build and audit verification commands. `ztd` is an application that links a validated cryptographic module; it is not separately validated or certified as a cryptographic module under FIPS 140-3.

## Invariants

Ids are stable. Append the next free number in a topic. Do not renumber.

### Compliance scope (`INV-FIPS-SCOPE`)

| ID | Rule |
| :--- | :--- |
| INV-FIPS-SCOPE-01 | The `ztd` FIPS 140-3 compliance claim applies exclusively to Linux AMD64 binaries built with `GOFIPS140=v1.0.0` and deployed on Debian GNU/Linux 12 (Bookworm). The claim covers approved cryptographic services provided by CMVP Certificate #5247; it does NOT extend to other operating systems, architectures, binaries built without `GOFIPS140`, or processes launched with `GODEBUG=fips140=off`. |
| INV-FIPS-SCOPE-02 | A deployment remains within the compliance claim if and only if `./ztd version --fips` reports approved mode enabled, module version `v1.0.0`, and the deployed binary is the Linux AMD64 artifact generated by `make fips-build` or `make build-all`. |
| INV-FIPS-SCOPE-03 | Linking a validated module does NOT automatically satisfy every regulatory mandate governing an enterprise environment. Deploying organizations remain authoritative for external key strength, secure key generation, and approved use of cryptographic services. |

### Validated module (`INV-FIPS-MODULE`)

| ID | Rule |
| :--- | :--- |
| INV-FIPS-MODULE-01 | The linked cryptographic module is Go Cryptographic Module v1.0.0, validated under CMVP Certificate #5247 (active through April 26, 2031) at FIPS 140-3 Security Level 1. The module executes as a Multi-Chip Standalone software module. |
| INV-FIPS-MODULE-02 | Certificate #5247 provides no assurance regarding the minimum cryptographic strength of externally supplied keys, generated passwords, or parameters derived from external inputs. Deployments MUST independently assess external key material. |

### Build configuration (`INV-FIPS-BUILD`)

| ID | Rule |
| :--- | :--- |
| INV-FIPS-BUILD-01 | `GOFIPS140=v1.0.0` is a compile-time toolchain directive. Setting it at build time links the frozen, validated module and configures the executable's default runtime state to approved mode (`fips140=on`). The binary does NOT read `GOFIPS140` at runtime. |
| INV-FIPS-BUILD-02 | `make build-all` automatically compiles Linux targets with `GOFIPS140=v1.0.0`. Non-Linux targets (Darwin, Windows) explicitly unset it. Standard `make build` and `go install` do NOT link the validated module; production builds MUST use `make fips-build` or `make build-all`. |
| INV-FIPS-BUILD-03 | The binary MUST be statically linked with `CGO_ENABLED=0`. The Go Cryptographic Module is implemented entirely in pure Go and requires no CGO or dynamic external C libraries. |

### Runtime control (`INV-FIPS-RUNTIME`)

| ID | Rule |
| :--- | :--- |
| INV-FIPS-RUNTIME-01 | `GODEBUG=fips140=off` disables approved mode at process initialization, overriding the build-time default. This setting invalidates the FIPS compliance claim and MUST NOT be used in FIPS-regulated production environments. |
| INV-FIPS-RUNTIME-02 | `GODEBUG=fips140=only` activates Go's diagnostic enforcement mode, rejecting or panicking on non-approved operations. This is an assessment and debugging tool that can trigger crashes; it is NOT required by the module security policy and MUST NOT be enabled in production. |

## Procedures

### Compliance scope

`ztd` Linux AMD64 production binaries link Go Cryptographic Module v1.0.0 and initialize into FIPS 140-3 approved mode by default. The module is validated under NIST CMVP Certificate #5247 and CAVP Certificate A6650. This claim covers the invocation of approved cryptographic algorithms provided by that module on supported operating systems; it does not constitute a separate CMVP certification of the `ztd` platform binary.

To maintain compliance, all of the following conditions MUST be satisfied:
- The deployed binary is a Linux AMD64 artifact compiled with `GOFIPS140=v1.0.0` and `CGO_ENABLED=0`.
- The binary executes on the vendor-affirmed Debian GNU/Linux 12 (Bookworm) operating environment.
- `./ztd version --fips` reports approved mode enabled and module version `v1.0.0`.
- The deployment exclusively configures approved algorithms, key lengths, and external key material.

### Validated module

- **Module Name**: Go Cryptographic Module v1.0.0
- **CMVP Validation**: [Certificate #5247](https://csrc.nist.gov/projects/cryptographic-module-validation-program/certificate/5247), active through April 26, 2031
- **Algorithm Validation**: CAVP Certificate A6650
- **FIPS Standard**: FIPS 140-3, Security Level 1
- **Module Classification**: Multi-Chip Standalone Software Module

### Cryptographic services

When executing in approved mode, `ztd` routes all cryptographic calls through the validated module:

- **Transport Layer Security (TLS 1.3 & mTLS)**: Enforces TLS 1.3 exclusively. Configures post-quantum hybrid key exchange `X25519MLKEM768`, alongside ECDH on NIST curves P-384 and P-256. Standalone X25519 is explicitly omitted from curve preferences. The hybrid key exchange uses ML-KEM as specified in FIPS 203.
- **Platform PKI & Certificates**: Generates root CA, intermediate CA, and Gateway serving keys on ECDSA P-256. The Gateway signs only P-256 certificate signing requests (CSRs) for CLI, Operator, Hub, and app leaf certificates. Certificate and CRL signatures use ECDSA with SHA-256. CA certificates whose signature algorithm is Ed25519 are rejected.
- **Application Signatures**: Consensus votes, actuator action event receipts, capabilities, platform enrollment proofs, public-feed proofs, and compliance report signatures use Ed25519. Notary approvals use ECDSA P-256 with SHA-256: signed CLI approval proofs verify against an ECDSA P-256 certificate, and passkey assertions verify under the credential algorithm the authenticator registered. EdDSA key generation, verification, and signing are approved services under Certificate #5247.
- **Symmetric Data Protection**: Local vault stores, execution events, and token maps use AES-256-GCM. Vault key derivation uses HKDF-SHA-256, keyed content digests use HMAC-SHA-256, and state hashing uses SHA-256.
- **Random Number Generation**: Key generation, nonces, and session tokens utilize `crypto/rand`, implemented in approved mode via an SP 800-90A Deterministic Random Bit Generator (DRBG) seeded by host entropy.
- **Passkey WebAuthn**: The Gateway advertises ES256 (ECDSA P-256 with SHA-256) as the primary credential algorithm for WebAuthn passkey registration.
- **SSH Operations**: Governed native SSH tools use `golang.org/x/crypto/ssh`, which automatically filters out non-approved ciphers, MACs, and key-exchange algorithms in FIPS mode.

### Operating environment

The compliance claim is formally affirmed on:
- **Operating System**: Debian GNU/Linux 12 (Bookworm)
- **Architecture**: AMD64 (x86_64)
- **Compilation Environment**: `CGO_ENABLED=0 GOFIPS140=v1.0.0 go build`

Artifacts compiled for Linux ARM64, Linux 386, Windows, or macOS are excluded from the FIPS compliance claim.

### Build configuration

Compilation with `GOFIPS140=v1.0.0` embeds approved mode into the resulting binary:

```bash
# Build the dedicated Linux AMD64 FIPS binary
make fips-build

# Or build all platform targets (Linux AMD64 automatically includes FIPS)
make build-all
```

The build writes `bin/ztd-fips-linux-amd64`, writes its SHA-256 digest to `bin/ztd-fips-linux-amd64.sha256`, and copies the binary to the repository root as `ztd-fips`.

### Runtime verification

Verify the active cryptographic mode on the deployed host:

```bash
./ztd version --fips
```

The `--fips` block follows the build metadata lines and prints:
```text
FIPS 140-3 mode:     enabled
FIPS enforcement:    disabled
FIPS module version: v1.0.0
```

The command exits with return code `0` when approved mode is enabled. When enforcement is disabled, it also prints a warning and still exits `0`. When approved mode is disabled, it prints remediation guidance and exits with a non-zero code.

### CI verification

The `CI (FIPS 140-3)` workflow (`.github/workflows/build-and-test-fips.yml`) runs on GitHub-hosted `ubuntu-latest` runners. Those runners are not the affirmed Debian GNU/Linux 12 operating environment, so the workflow does not validate the affirmed operating environment itself. The workflow validates:
1. `make fips-verify`: Compiles `bin/ztd-fips-linux-amd64` and executes `./ztd-fips version --fips` under `GODEBUG=fips140=only`.
2. `make test-unit` and `make test-integration` compile with `GOFIPS140=v1.0.0` and execute in approved mode.
3. Binary inspection confirms static linkage with zero shared library dependencies (`make verify-static` checks `file` and `ldd` output for the FIPS binary).

## Anti-patterns

- Deploying binaries built with ordinary `make build` or `go install` without `GOFIPS140=v1.0.0` in FIPS-regulated environments (INV-FIPS-BUILD-02).
- Operating `ztd` with `GODEBUG=fips140=off` in FIPS environments (INV-FIPS-RUNTIME-01).
- Deploying Windows or macOS binaries under a FIPS compliance claim (INV-FIPS-SCOPE-01).
- Enabling diagnostic enforcement (`GODEBUG=fips140=only`) in production runtimes (INV-FIPS-RUNTIME-02).
- Failing to verify the binary status with `./ztd version --fips` during deployment audits (INV-FIPS-SCOPE-02).
