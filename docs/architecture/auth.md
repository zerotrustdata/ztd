# Authentication & Authorization Architecture

## Purpose

Documents how ztd separates authentication (establishing principal identity) from authorization (determining whether that principal may access a route or govern a transaction). Defines route classification, WebAuthn passkeys, mTLS with SPIFFE SANs, CLI signatures, session token handling, operator binding, and the integration points between CLI, browser, workload, and governance layers.

## Invariants

Ids are stable. Append the next free number within each group; do not renumber.

### Identity and authentication (`INV-AUTH-ID`)

| ID | Rule |
| --- | --- |
| INV-AUTH-ID-01 | Every authenticated request carries a principal extracted from the authenticated transport (mTLS certificate SPIFFE URI SAN, validated browser session cookie, or verified JWT). A caller-supplied identity header cannot replace that transported identity. |
| INV-AUTH-ID-02 | SPIFFE identity URIs bind user, CLI session, operator session, and application identities to certificate SANs. The gateway validates revocation and matches the certificate identity to the referenced server-side session before accepting a request. |
| INV-AUTH-ID-03 | CLI sessions and certificates expire in 7 days. Web sessions expire in 24 hours. Operator identities do not expire based on registration document age. Operator authentication requires a valid, non-revoked mTLS certificate, a non-terminated identity, and an active linked user. An expired certificate cannot authenticate; expired CLI sessions require `ztd auth refresh`. |
| INV-AUTH-ID-04 | CLI private keys and workload private keys are generated by the requesting component; they are not transmitted to the gateway. The CLI key (`.ztd/cli.key`), each app key (`.ztd/apps/<name>.key`), and the pending app enrollment state (`.ztd/pki/pending-enrollment/app_<name>.json`, which holds a key and the enrollment token) are sealed under the keystore master key and never touch disk in the clear. They load by unsealing in memory then `tls.X509KeyPair`; a missing or locked master key fails closed, and a plaintext file in a sealed path is refused with `ErrIdentityFilePlaintext` (unseal failures wrap `ErrIdentityFileUnseal`). There is no migration or plaintext fallback. The pending state is removed on completion, denial, and expiry. |
| INV-AUTH-ID-05 | A governed envelope submitted to `POST /api/v1/governance/envelopes` that names neither `operator_id` nor `operator_session_id` is admitted at the transport boundary only as an application platform-record write: the action is `DOCUMENT_UPDATE` or `DOCUMENT_DELETE`, `source_component` is `AGENT` or `CLIENT`, `acting_app_id` is set, and a certificate URI SAN equals the app SPIFFE ID for that `acting_app_id`. Any other unbound action fails with `ErrIdentityBindingFailed`: mutations such as `EXECUTE_BASH`, `FILE_EDIT`, `RESTORE_FILE`, `MCP_CALL`, and `SHUTDOWN`, and reads such as `FS_READ`, `FS_LIST`, `FS_GREP`, and `FETCH_LOGS`. This binding authenticates the submitting application. It adds no L2 or L3 proof, and L4 still verifies the envelope. |
| INV-AUTH-ID-06 | A browser-session route derives the web session ID from the validated cookie value, which is the persisted web-session document's key. The stored session body does not carry its own ID, so downstream SSE routing never receives an empty web session ID. |

### Route classification (`INV-AUTH-ROUTE`)

| ID | Rule |
| --- | --- |
| INV-AUTH-ROUTE-01 | Routes are classified as public (`RouteAuthNone`), mTLS-only (`RouteAuthMTLS`), browser-session-only (`RouteAuthWebSession`), or dual-auth (`RouteAuthDual`). The route registry matches exact paths before prefixes and applies mTLS to unknown HTTPS paths as a fail-closed default. |
| INV-AUTH-ROUTE-02 | Public routes (health checks, trust discovery, landing page, public deploy scripts, bootstrap initiation, token-scoped recovery/enrollment request and status endpoints, and console SPA) are exposed on plain HTTP without requiring authentication. |
| INV-AUTH-ROUTE-03 | Unknown HTTPS routes require mTLS authentication by default; an unclassified route does not become public. |
| INV-AUTH-ROUTE-04 | Dual-auth routes (platform enrollment owner review and decisions, SSE consumer streams, operator management and detail, audit read routes, direct approval response, and Swagger documentation) try mTLS first and otherwise validate the browser-session cookie. mTLS is preferred when a client certificate is present. |
| INV-AUTH-ROUTE-05 | CLI refresh (`/api/v1/auth/cli/refresh`) and CLI logout (`/api/v1/auth/cli/logout`) are the only routes admitted on a verified CLI certificate alone, whatever state its CLI session is in. Every other CLI route fails closed on an expired, missing, or inactive session. Logout grants nothing refresh does not: any holder of an unrevoked certificate can already refresh and then log out. |

### Session and certificate lifecycle (`INV-AUTH-SESSION`)

| ID | Rule |
| --- | --- |
| INV-AUTH-SESSION-01 | Enrollment, recovery, rotation, and refresh decisions are made by comparing local credential state with gateway trust anchors and session validity. An offline identity can be inspected and reused; gateway discovery is best-effort. |
| INV-AUTH-SESSION-02 | Reusing a CLI certificate is idempotent when the local certificate matches the gateway root, has an active session server-side, and is not expiring within 24 hours. No new certificate is issued. |
| INV-AUTH-SESSION-03 | Certificate rotation issues exactly one replacement certificate and revokes the prior one. Rotation occurs automatically within 24 hours of expiry and can be forced with `--rotate-cli`. |
| INV-AUTH-SESSION-04 | Session refresh (`ztd auth refresh`) uses the still-valid certificate as proof of identity to mint a replacement server-side session. It is the recovery path when the certificate is valid but the session is expired or missing. |
| INV-AUTH-SESSION-05 | `ztd logout` terminates every web and CLI session of the authenticated user, on every machine, and unbinds every operator bound to those sessions. Scope `all` is the default; `web` and `cli` narrow it. Operator sessions are unbound, never terminated. Other users' sessions, bindings, and certificates are untouched. |
| INV-AUTH-SESSION-06 | A CLI logout revokes the certificate of every CLI session the user held (and the certificate that authenticated the request), because refresh re-issues a session for any unrevoked certificate regardless of the old session's state: deactivating sessions alone is not a logout. Revocation is the last step so a failure leaves the caller able to retry, and it skips serials already revoked so an earlier revocation keeps its reason and time. |
| INV-AUTH-SESSION-07 | The CLI deletes its local credentials only after the Gateway confirms a CLI-scope logout; an unreachable Gateway changes nothing. `--local-only` is the single path that skips the Gateway: it deletes local credentials and does not end any server-side session, operator binding, or certificate. |

### Operator binding (`INV-AUTH-OP-BIND`)

| ID | Rule |
| --- | --- |
| INV-AUTH-OP-BIND-01 | The embedded operator is a binding record (not an enrollment lease) anchoring the first user's sessions. It holds no certificate and persists under the deterministic ID `embedded-operator`. |
| INV-AUTH-OP-BIND-02 | First-user bootstrap claims the embedded-operator document, recording the user and operator session ID. The claim is the explicit human enrollment act. A same-user reclaim is idempotent; a different user's claim is rejected. |
| INV-AUTH-OP-BIND-03 | Unified auth middleware stamps operator identity from the persisted session record, not from request headers. Headers that name an operator session outside the persisted binding are rejected. |
| INV-AUTH-OP-BIND-04 | CLI session refresh and rotation preserve the prior session's operator binding (or, when stale or missing, resolve the embedded operator, which is always a Data operator and is therefore the default, or else an active dedicated Data Operator). Recovery binds an active operator session (preferring the embedded operator) or mints a dedicated recovery operator when none exists. |
| INV-AUTH-OP-BIND-05 | A CLI session bound to many operators admits every bound operator session as a request's operator identity, not only the primary. The operator ID header, when sent, MUST match the named bound session, and the bound operator MUST belong to the session's user. A session outside the persisted bound list is rejected. |

### External identity providers (`INV-AUTH-JWT`)

| ID | Rule |
| --- | --- |
| INV-AUTH-JWT-01 | JWT authentication is scoped to explicitly wrapped external-client MCP and A2A surfaces when JWKS is configured. It does not grant access to arbitrary administrative routes. |
| INV-AUTH-JWT-02 | RS256 signatures are verified using the token's key identifier from the configured JWKS. Issuer, audience, subject, and temporal constraints are validated. |
| INV-AUTH-JWT-03 | The first valid JWT for a subject provisions an internal user. The configured role claim maps to an internal persona. |

## Route Authentication and Classification

The Gateway's unified auth middleware (`gateway_auth.go`) classifies each route into one of four distinct authentication policies:

```text
Incoming Request
      │
      ├─ Match route in RouteAuthRegistry
      │
      ├─► RouteAuthNone
      │   └── Admitted directly (Health, Discovery, Token-scoped bootstrap/recovery)
      │
      ├─► RouteAuthMTLS
      │   └── Enforces TLS 1.3 peer certificate with SPIFFE SAN + Server-side Session
      │
      ├─► RouteAuthWebSession
      │   └── Validates ztd_web_session_cookie against persisted WebSession document
      │
      ├─► RouteAuthDual
      │   ├── Checks client certificate first (mTLS)
      │   └── Falls back to ztd_web_session_cookie if no certificate presented
      │
      └─► Unmatched HTTPS Route
          └── Defaults to RouteAuthMTLS (fail-closed)
```

1. **Public routes (`RouteAuthNone`)**: Require no credentials. Served on plain HTTP (port 8080) and HTTPS (port 8443). Includes health checks (`/api/v1/health`), landing page (`/`), state discovery (`/api/v1/state`), PKI bootstrap (`/.well-known/ztd/pki/`, `/.well-known/ztd/bin/`), deploy scripts (`/ztd-deploy.sh`, `/ztd-deploy.ps1`), first-user bootstrap (`/api/v1/auth/bootstrap`, `/status`), logout (`/api/v1/auth/logout`), token-scoped CLI recovery, token-scoped platform enrollment endpoints (`/api/v1/auth/platform-enrollments/{request,status,complete}`, including long-poll `status?token=...&wait=true`), the Operator bootstrap websocket (`/ws/operator/bootstrap`), and the Console SPA (`/console/`).
2. **mTLS-only routes (`RouteAuthMTLS`)**: Require a verified client certificate. Includes privileged PKI CSR signing (`/api/pki/csr/sign`), producer endpoints (`/api/v1/observe/producer/*`), operator internal controls (`/api/v1/operators/validate`, `/target`, `/commands`, `/stop`, `/sessions/`), CLI rotation (`/api/v1/auth/cli/rotate`), CLI session refresh (`/api/v1/auth/cli/refresh`), CLI bind/unbind (`/api/v1/auth/cli/bind`, `/unbind`), CLI logout (`/api/v1/auth/cli/logout`), CLI session info (`/api/v1/auth/cli/session`), and CLI recovery approval via mTLS (`/api/v1/auth/cli/recovery/approve-cli`).
3. **Browser-session routes (`RouteAuthWebSession`)**: Validate the `ztd_web_session_cookie` against the persisted web-session record. The user ID comes from the record and the web session ID is the cookie value (`INV-AUTH-ID-06`). Includes user profiles (`/api/v1/users/`), session introspection (`/api/v1/auth/sessions/`), browser transaction approvals (`/api/v1/approvals/`), browser passkey management (`/api/v1/auth/passkeys/`), and browser CLI recovery approval (`/api/v1/auth/cli/recovery/approve`).
4. **Dual-auth routes (`RouteAuthDual`)**: Try mTLS first and otherwise validate the browser-session cookie. mTLS is preferred when a certificate is present. Includes SSE streams (`/api/v1/sse/stream`, `/api/v1/sse/events`), operator list and binding (`/api/v1/operators`, `/bind`, `/unbind`, `/{id}/`), owner audit logs (`/api/v1/audit/events`, `/summary`, `/verify`), direct denial response (`/api/v1/approvals/respond`), platform enrollment owner review and consensus binding (`/api/v1/auth/platform-enrollments/{pending,enrolled,decision,decisions,revoke,consensus}`), and OpenAPI documentation (`/swagger/doc.json`).
5. **Unknown HTTPS routes**: Default to mTLS authentication as a fail-closed rule.

## WebAuthn Passkey Authentication

The Console uses WebAuthn passkeys for passwordless authentication, human-presence attestation, and L3 Notary approvals:

- **Authenticators**: Platform authenticators (Windows Hello, Apple Touch ID / Face ID), roaming security keys (FIDO2 / YubiKey), and synced passkeys satisfy the ceremony.
- **User Verification**: Mandatory (`VerificationRequired`) across registration, login, and L3 passkey verification ceremonies.
- **Clone Detection**: The Gateway maintains the sign counter and timestamp. If an authenticator reports a non-increasing counter (`CloneWarning`), the assertion is rejected with `ErrPasskeyCloneDetected`.
- **Lockout Prevention**: Attempting to revoke the user's sole remaining passkey fails with HTTP 409 Conflict (`ErrLastPasskeyRevoke`).
- **Web Session**: Successful passkey authentication issues a 24-hour browser session (`WebSessionTTL = 24h`) and sets the `ztd_web_session_cookie` (HttpOnly, Secure, SameSite=Lax).

## Mutual TLS and SPIFFE Identity Binding

Every workload (CLI, Operator, App) connecting over mTLS presents an X.509 certificate signed by the Operator Intermediate CA with a SPIFFE URI SAN under the canonical `ztd.local` trust domain:

| Workload Type | SPIFFE ID Format | Description |
| :--- | :--- | :--- |
| **Governed Operator** | `spiffe://ztd.local/operator/<org>/<op>/<session>` | Outbound operator session identity |
| **CLI / Client** | `spiffe://ztd.local/cli/<user>/<cli_session>` | Local CLI session identity |
| **Application** | `spiffe://ztd.local/app/<application_id>` | Delegated app/agent workload identity |
| **User Principal** | `spiffe://ztd.local/user/<user_id>` | Human user principal identity |
| **Gateway Hub** | `spiffe://ztd.local/hub/operator-listen` | Gateway listener serving identity |
| **Gateway Peer** | `spiffe://ztd.local/gateway/<gateway_id>` | Peer-to-peer federated gateway identity |

Workload leaf certificates have a 7-day validity (`WorkloadCertTTL = 7 * 24h`). Revocation is enforced on every mTLS request via CRL check at `/.well-known/ztd/pki/crl`.

## CLI Enrollment, Signatures, and Lifecycle

The `ztd login` and `ztd auth enroll user` commands manage the CLI identity state machine:

| Local and Gateway State | Action |
| :--- | :--- |
| No local identity and no gateway user | Bootstrap first owner and issue CLI identity |
| No local identity on initialized gateway | Request human-approved recovery via Console or `ztd auth approve-recovery` |
| Valid cert, matching gateway root, active session | Idempotent reuse; no new cert issued |
| Valid cert expiring within 24 hours | Rotate certificate via authenticated mTLS (`/api/v1/auth/cli/rotate`) |
| Valid cert but expired server-side session | Refresh session via `ztd auth refresh` (`/api/v1/auth/cli/refresh`) |
| Expired cert or mismatched gateway root | Recover identity or bootstrap if gateway is uninitialized |

- **Local Private Key**: Generated locally via ECDSA P-256 and never transmitted over the wire.
- **Refresh Flow**: `ztd auth refresh` uses the still-valid certificate as proof of identity to mint a replacement server-side session, preserving operator bindings.
- **Logout Flow**: `ztd logout` calls `POST /api/v1/auth/cli/logout` over mTLS. The Gateway terminates web and CLI sessions, unbinds operators, and revokes CLI certificates. Local credentials are deleted only after Gateway confirmation (or immediately via `--local-only`).

## Session Token Handling and Operator Binding

### Operator Binding Architecture

CLI commands bind to Operator sessions through explicit server-side mappings:

```text
CLI Certificate (SPIFFE URI SAN)
      │
      ▼
CLI Session (cli_session_id)
      │
      ├─► Primary Binding: operator_session_id
      │
      └─► Multi-Operator Binding: bound_operator_session_ids (up to 5,000)
```

1. **Embedded Operator**: Deterministic ID `embedded-operator`. Anchors first-user bootstrap without an enrollment lease.
2. **Binding Mutation**: Managed via `ztd operator bind <operator-session-id>...` (`POST /api/v1/auth/cli/bind`). The Gateway validates that each target operator session is active and owned by the calling user.
3. **Session Stamping**: The Gateway stamps the active operator identity from the persisted session record, rejecting forged caller-supplied identity headers (`INV-AUTH-OP-BIND-03`).

## Platform Workload Enrollment

Workloads (Operators and applications) enroll via owner-approved workflows governed by the active posture (`constants.Posture`):

1. **Operator Enrollment**: Outbound Operators enroll exclusively over the bootstrap WebSocket (`/ws/operator/bootstrap`). On a single socket, the Operator sends a `request` frame (CSRs, system fingerprint, `token_hash`, runtime config), immediately sends `complete` with proof of possession, holds for owner approval, and receives a `bundle` frame with certificates, session identity, the Gateway's `Posture`, and the bound L2 consensus application's public key (`OperatorL2Trust`).
2. **Application Enrollment (`PLATFORM_COMPONENT_KIND_APPLICATION`)**: Applications generate keys and CSRs locally, persist an opaque token (sealed, with the key, in the pending enrollment state), and submit to `POST /api/v1/auth/platform-enrollments/request`. The request expires in 30 minutes:
   - **Under `doctrine` and `consensus` (`!posture.RequiresL3()`)**: An authenticated owner CLI (`CLISession` over mTLS) approves its own app enrollment in-line during `ztd mcp agent run <agent>` or `ztd auth enroll app <name>` (`POST /api/v1/auth/platform-enrollments/decision`), with no passkey ceremony and no second command required.
   - **Under `ratify` and `notary` (`posture.RequiresL3()`)**: `PLATFORM_ENROLLMENT_DECIDE` and `PLATFORM_ENROLLMENT_REVOKE` remain L3-gated. Submitting a decision or revocation without an inline passkey proof suspends the `GovernanceEnvelope` via `mcp.GatewayService.SuspendGovernanceEnvelope` (`StoreSuspendedTransaction`) and returns HTTP `202 Accepted` (`status: "l3_required"`, `posture`, `tx_hash`, `approval_url` at `/console/approve/<tx_hash>`, `expires_at`, `message`). In the CLI, `ztd mcp agent run` / `ztd auth enroll app` prints `posture.HumanApprovalReason()`, the approval URL, and the expiry, then holds `GET /api/v1/auth/platform-enrollments/status?token=...&wait=true` (woken event-driven via `EnrollmentsDecided` at the `DocumentStoreService.DecidePlatformEnrollments` commit boundary when `ResumeWithL3Proof` replays the envelope). In the Console (`ApprovalsView.tsx`), a `202 l3_required` response from `POST /api/v1/auth/platform-enrollments/decision` immediately triggers the WebAuthn passkey ceremony (`approveTransaction(tx_hash)`) in-line.
   - **Follow-On Completion Mutations (`AuthorizedByDecision`)**: Once `PLATFORM_ENROLLMENT_DECIDE` commits, the follow-on completion mutations (`PLATFORM_ENROLLMENT_ISSUE`, `PLATFORM_ENROLLMENT_PERSIST_POLICY`, `PLATFORM_ENROLLMENT_CREATE_SESSION`) at `POST /api/v1/auth/platform-enrollments/complete` carry `_authorized_by_decision` (`ActionType.AuthorizedByDecision() == true`) and inherit authority from the committed decision (`governance.L3Required` is false). `HandlePersistPolicy` and `HandleCreateSession` strictly require and field-by-field match the committed issuance (`ErrPlatformEnrollmentIssuanceNotCommitted`, `ErrPlatformEnrollmentIssuanceMismatch`). Upon completion, an enrolled application receives its mTLS client certificate and its Ed25519 public key is registered in `trusted_signers`.
3. **Consensus Application Binding (`PLATFORM_ENROLLMENT_BIND_CONSENSUS`)**: Any enrolled `PLATFORM_COMPONENT_KIND_APPLICATION` can be bound as the Gateway's single consensus provider (`constants.DocIDConsensusBinding` in `constants.CollectionConsensus`) via `POST /api/v1/auth/platform-enrollments/consensus`. This bootstrap action (`IsBootstrapAction() == true`) is exempt from L2 gating across all postures and remains L3-gated under `ratify` and `notary`.
4. **Revocation**: The owner revokes completed enrollments via `ztd auth enroll revoke <request-id>` (`PLATFORM_ENROLLMENT_REVOKE`, L3-gated under `ratify` and `notary`). The Gateway revokes certificates, terminates operator sessions, and immediately disconnects corresponding WebSocket channels.

## Authorization and Governance Interlock

Authentication admits a principal to a route. Authorization determines whether that principal may execute a governed transaction through the five-layer pipeline:

| Layer | Enforcement | Responsibility |
| :--- | :--- | :--- |
| **L1 Doctrine** | Universal | Static heuristics, blacklist patterns, Gitleaks secrets signatures, OWASP CRS |
| **L2 Consensus** | Posture-gated (`RequiresL2()`) | Bound consensus application's Ed25519 signature over `<tx_hash>\|<decision>` |
| **L3 Notary** | Posture-gated (`governance.L3Required`) | WebAuthn human authorization assertion over transaction hash |
| **L4 Warden** | Universal | Nonce reservation, replay prevention, hash integrity, Merkle root, proof verification |
| **L5 Actuator** | Universal | JIT capability minting, payload rehydration, command dispatch, signed receipts |

Gateway-mode L3 approval requires a WebAuthn assertion; there is no CLI-only L3 approval on the Gateway. Denials are submitted via `POST /api/v1/approvals/respond` with `approved: false`. The Gateway resubmits the suspended envelope with `L3Metadata.denied` set; the executing runtime's L4 rejects it in every posture with `GOVERNANCE_REJECTION_CODE_L3_DENIED`, and its L5 signs the rejection receipt. The deny needs no approval proof because it can only stop execution, and `denied` is outside the transaction hash. The response and the `approval.completed` event both carry the signed receipt.

## Anti-patterns

- **Bypassing route classification**: Calling internal handlers directly instead of routing through the Gateway (`INV-AUTH-ROUTE-01`).
- **Trusting identity headers**: Accepting caller-supplied headers instead of extracting identity from the transport certificate SPIFFE SAN (`INV-AUTH-ID-01`).
- **Re-enrolling instead of refreshing**: Re-running enrollment when `ztd auth refresh` suffices for a valid certificate with an expired session (`INV-AUTH-SESSION-04`).
- **Refreshing with an expired certificate**: Attempting `ztd auth refresh` with an expired certificate instead of running `ztd auth enroll user` (`INV-AUTH-SESSION-03`).
- **Modifying host PKI to bypass tests**: Mutating OS trust stores rather than using isolated test fixtures.
- **Unchecked last passkey revocation**: Allowing a user to delete their sole remaining passkey (`ErrLastPasskeyRevoke`).
