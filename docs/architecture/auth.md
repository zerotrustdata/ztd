# Authentication & Authorization Architecture

## Purpose

Documents how ztd separates authentication (establishing principal identity) from authorization (determining whether that principal may access a route or govern a transaction). Defines route classification, WebAuthn passkeys, mTLS with SPIFFE SANs, CLI signatures, session token handling, operator binding, and the integration points between CLI, browser, workload, and governance layers.

## Invariants

Ids are stable. Append the next free number within each group; do not renumber.

### Identity and authentication (`INV-AUTH-ID`)

| ID | Rule |
| --- | --- |
| INV-AUTH-ID-01 | Every authenticated request carries a principal extracted from the authenticated transport (mTLS certificate SPIFFE URI SAN, validated WebSession cookie, or verified JWT). A caller-supplied identity header cannot replace that transported identity. |
| INV-AUTH-ID-02 | SPIFFE identity URIs bind user, CLISession, OperatorSession, and application identities to certificate SANs. The gateway validates revocation and matches the certificate identity to the referenced server-side session before accepting a request. |
| INV-AUTH-ID-03 | CLISessions and certificates expire in 7 days. WebSessions expire in 24 hours. Operator identities do not expire based on registration document age. Operator authentication requires a valid, non-revoked mTLS certificate, a non-terminated identity, and an active linked user. An expired certificate cannot authenticate; expired CLISessions require `ztd auth refresh`. |
| INV-AUTH-ID-04 | CLI private keys and workload private keys are generated by the requesting component; they are not transmitted to the gateway. The CLI key (`.ztd/cli.key`), each app key (`.ztd/apps/<name>.key`), and the pending app enrollment state (`.ztd/pki/pending-enrollment/app_<name>.json`, which holds a key and the enrollment token) are sealed under the keystore master key and never touch disk in the clear. They load by unsealing in memory then `tls.X509KeyPair`; a missing or locked master key fails closed, and a plaintext file in a sealed path is refused with `ErrIdentityFilePlaintext` (unseal failures wrap `ErrIdentityFileUnseal`). There is no migration or plaintext fallback. The pending state is removed on completion, denial, and expiry. |
| INV-AUTH-ID-05 | A governed envelope submitted to `POST /api/v1/governance/envelopes` that names neither `operator_id` nor `operator_session_id` is admitted at the transport boundary only as an application platform-record write: the action is `DOCUMENT_UPDATE` or `DOCUMENT_DELETE`, `source_component` is `AGENT` or `CLIENT`, `acting_app_id` is set, and a certificate URI SAN equals the app SPIFFE ID for that `acting_app_id`. Any other unbound action fails with `ErrIdentityBindingFailed`: mutations such as `EXECUTE_BASH`, `FILE_EDIT`, `RESTORE_FILE`, `MCP_CALL`, and `SHUTDOWN`, and reads such as `FS_READ`, `FS_LIST`, `FS_GREP`, and `FETCH_LOGS`. This binding authenticates the submitting application. It adds no L2 or L3 proof, and L4 still verifies the envelope. |
| INV-AUTH-ID-06 | A browser-session route derives the WebSession ID from the validated cookie value, which is the persisted WebSession document's key. The stored WebSession body does not carry its own ID, so downstream SSE routing never receives an empty web session ID. |
| INV-AUTH-ID-07 | A CLI certificate's URI SAN names the CLISession it authenticates, and that CLISession keeps the ID for its whole life. Every path that persists a CLISession signs the certificate with that ID first (bootstrap, registration, recovery, platform enrollment, rotation), and refresh extends the session in place (`INV-AUTH-SESSION-08`), so no path mints an ID a certificate does not name. A request whose header names a CLISession other than the SAN is rejected with `ErrMTLSIdentityMismatch`. No certificate fingerprint substitutes for that match. |
| INV-AUTH-ID-08 | A governed envelope's `cli_session_id` claim that is admitted on an Operator certificate or an app certificate, rather than on the claimed CLISession's own CLI certificate, must name a CLISession that is active and unexpired, owned by the authenticated user, and, when the CLISession records operator bindings, bound to the envelope's `operator_session_id`. Any other claim is refused with `ErrIdentityBindingFailed`. An empty claim is not checked. |

### Route classification (`INV-AUTH-ROUTE`)

| ID | Rule |
| --- | --- |
| INV-AUTH-ROUTE-01 | Routes are classified as public (`RouteAuthNone`), mTLS-only (`RouteAuthMTLS`), browser-session-only (`RouteAuthWebSession`), or dual-auth (`RouteAuthDual`). The route registry matches exact paths before prefixes and applies mTLS to unknown HTTPS paths as a fail-closed default. |
| INV-AUTH-ROUTE-02 | The plain HTTP listener (port 8080) serves without authentication only the discovery and bootstrap routes: health and state, first-user bootstrap and its status, the PKI CA bundle and fingerprint, the Operator binary download prefix, the Linux and Windows deploy scripts, token-scoped CLI recovery and platform enrollment request, status, and complete, and the Operator bootstrap WebSocket. Every other plain HTTP request, including the landing page, the console SPA, and the approval page, receives a 301 redirect to HTTPS. |
| INV-AUTH-ROUTE-03 | Unknown HTTPS routes require mTLS authentication by default; an unclassified route does not become public. |
| INV-AUTH-ROUTE-04 | Dual-auth routes (platform enrollment owner review and decisions, SSE consumer streams, operator management and detail, audit read routes, direct approval response, and Swagger documentation) try mTLS first and otherwise validate the browser-session cookie. mTLS is preferred when a client certificate is present. |
| INV-AUTH-ROUTE-05 | CLI refresh (`/api/v1/auth/cli/refresh`) and CLI logout (`/api/v1/auth/cli/logout`) are the only routes admitted on a verified CLI certificate alone, whatever state its CLISession is in. Admission checks the certificate, its URI SAN against the header CLISession, and the user. Refresh then requires the CLISession to exist and be active: an expired CLISession is recovered, a deactivated one is refused with 409, and a missing one with 401. Logout requires the CLISession the certificate names, so an Operator certificate cannot log out its owner. Every other CLI route fails closed on an expired, missing, or inactive CLISession. Logout grants nothing refresh does not: any holder of an unrevoked certificate can already refresh and then log out. |

### Session and certificate lifecycle (`INV-AUTH-SESSION`)

| ID | Rule |
| --- | --- |
| INV-AUTH-SESSION-01 | Enrollment, recovery, rotation, and refresh decisions are made by comparing local credential state with gateway trust anchors and session validity. An offline identity can be inspected and reused; gateway discovery is best-effort. |
| INV-AUTH-SESSION-02 | Reusing a CLI certificate is idempotent when the local certificate matches the gateway root, has an active CLISession server-side, and is not expiring within 24 hours. No new certificate is issued. |
| INV-AUTH-SESSION-03 | Certificate rotation issues exactly one replacement certificate and revokes the prior one. Rotation occurs automatically within 24 hours of expiry and can be forced with `--rotate-cli`. |
| INV-AUTH-SESSION-04 | Session refresh (`ztd auth refresh`) uses the still-valid certificate as proof of identity to extend the CLISession the certificate names, in place (`INV-AUTH-SESSION-08`). It is the recovery path when the certificate is valid but its CLISession is expired. A CLISession the gateway no longer has is not recreated under the certificate's name: the refresh is refused with 401, and recovery is re-enrollment (`ztd auth enroll user`). |
| INV-AUTH-SESSION-05 | `ztd logout` terminates every WebSession and CLISession of the authenticated user, on every machine, and unbinds every operator bound to those sessions. `ztd logout` applies scope `all`; the `ztd logout web` and `ztd logout cli` subcommands narrow it. OperatorSessions are unbound, never terminated. Other users' WebSessions, CLISessions, bindings, and certificates are untouched. |
| INV-AUTH-SESSION-06 | A CLI-scope logout (`ztd logout cli`, or the default `all` scope) revokes the certificate of every CLISession the user ever held, plus the certificate that authenticated the request. Deactivating CLISessions alone is not a logout: the certificate stays signed by the Gateway CA until it expires, and revocation is what the PKI check (`PKIAuthority.VerifyCertificate`) and the CLI L3 verifier consult. Revocation is the last step so a failure leaves the caller able to retry, and it skips serials already revoked so an earlier revocation keeps its reason and time. |
| INV-AUTH-SESSION-07 | The CLI deletes its local credentials only after the Gateway confirms a CLI-scope logout; an unreachable Gateway changes nothing. `--local-only` is the single path that skips the Gateway: it deletes local credentials and does not end any server-side session, operator binding, or certificate. |
| INV-AUTH-SESSION-08 | Refresh extends the caller's CLISession in place. The CLISession keeps its ID, certificate fingerprint and serial, system fingerprint, login method, and creation time. All three expiry fields move to `CLISessionTTL` (7 days) from now, and the operator binding is rewritten to the one the caller resolves. The write is conditional on `is_active=true`: a deactivated (logged-out) CLISession is refused with 409 and never revived, and a CLISession owned by another user is reported as missing. No CLISession is minted. |

### Operator binding (`INV-AUTH-OP-BIND`)

| ID | Rule |
| --- | --- |
| INV-AUTH-OP-BIND-01 | The embedded operator is a binding record (not an enrollment lease) anchoring the first user's sessions. It holds no certificate and persists under the deterministic ID `embedded-operator`. |
| INV-AUTH-OP-BIND-02 | First-user bootstrap claims the embedded-operator document, recording the user and operator session ID. The claim is the explicit human enrollment act. A same-user reclaim is idempotent; a different user's claim is rejected. |
| INV-AUTH-OP-BIND-03 | Unified auth middleware stamps operator identity from the persisted CLISession record, not from request headers. Headers that name an OperatorSession outside the persisted binding are rejected. |
| INV-AUTH-OP-BIND-04 | CLISession refresh re-resolves the operator binding in place: the user's registry-active Data operator first (the embedded operator, which is always a Data operator and is therefore the default, then a dedicated Data Operator), else the CLISession's own binding while that OperatorSession is still active for the user, else the user's active OperatorSession. With none, refresh returns 409 and the caller re-enrolls. Rotation carries the binding to its replacement CLISession. Recovery binds an active OperatorSession (preferring the embedded operator) or mints a dedicated recovery operator when none exists. |
| INV-AUTH-OP-BIND-05 | A CLISession bound to many operators admits every bound OperatorSession as a request's operator identity, not only the primary. The operator ID header, when sent, MUST match the named bound OperatorSession, and the bound operator MUST belong to the CLISession's user. An OperatorSession outside the persisted bound list is rejected. |
| INV-AUTH-OP-BIND-06 | A bind or unbind updates the operator binding of the caller's active CLISession in place. The CLISession keeps its CLI session ID and certificate grounding (fingerprint and serial), so the certificate's URI SAN keeps naming the CLISession that signed CLI approvals are checked against, and the CLISession's SSE streams stay subscribed. A missing, inactive, or other-user CLISession is rejected, never replaced; `ztd auth refresh` is the recovery path. |
| INV-AUTH-OP-BIND-07 | A request authenticated by an Operator certificate never takes a CLISession identity from `X-ZTD-CLI-Session-ID`. The middleware stamps no CLISession on that path, so every CLI-only route rejects it: refresh (401), logout (401), rotation (401), session info (401), enrollment token generation (401), and bind or unbind (404, no caller session). Operator certificates pass the mTLS-only admission of bind and unbind, so the handler is the gate. The one header-driven check on the Operator path, `cliCertBoundToOperator`, admits a CLISession only when the certificate's own URI SAN names it and that CLISession is bound to the OperatorSession. |

### External identity providers (`INV-AUTH-JWT`)

| ID | Rule |
| --- | --- |
| INV-AUTH-JWT-01 | JWT authentication is scoped to explicitly wrapped external-client MCP and A2A surfaces when JWKS is configured. It does not grant access to arbitrary administrative routes. |
| INV-AUTH-JWT-02 | RS256 signatures are verified using the token's key identifier from the configured JWKS. Issuer, audience, subject, and temporal constraints are validated. |
| INV-AUTH-JWT-03 | The first valid JWT for a subject provisions an internal user. The configured role claim maps to an internal persona. |

## Route Authentication and Classification

The Gateway's unified auth middleware (`gateway_auth.go`) classifies each route into one of four distinct authentication policies:

```text
Incoming Request
      │
      ├─ Match route in RouteAuthRegistry
      │
      ├─► RouteAuthNone
      │   └── Admitted directly (Health, Discovery, Token-scoped bootstrap/recovery)
      │
      ├─► RouteAuthMTLS
      │   └── Enforces TLS 1.3 peer certificate with SPIFFE SAN + Server-side Session
      │
      ├─► RouteAuthWebSession
      │   └── Validates ztd_web_session_cookie against persisted WebSession document
      │
      ├─► RouteAuthDual
      │   ├── Checks client certificate first (mTLS)
      │   └── Falls back to ztd_web_session_cookie if no certificate presented
      │
      └─► Unmatched HTTPS Route
          └── Defaults to RouteAuthMTLS (fail-closed)
```

1. **Public routes (`RouteAuthNone`)**: Require no credentials. On HTTPS (port 8443) this includes health checks (`/api/v1/health`), landing page (`/`), state discovery (`/api/v1/state`), PKI bootstrap (`/.well-known/ztd/pki/`, `/.well-known/ztd/bin/`), deploy scripts (`/ztd-deploy.sh`, `/ztd-deploy.ps1`), first-user bootstrap (`/api/v1/auth/bootstrap`, `/api/v1/auth/bootstrap/status`), logout (`/api/v1/auth/logout`), token-scoped CLI recovery, token-scoped platform enrollment endpoints (`/api/v1/auth/platform-enrollments/{request,status,complete}`, including long-poll `status?token=...&wait=true`), the Operator bootstrap websocket (`/ws/operator/bootstrap`), the approval redirect (`/api/v1/approve/`), the passkey console and enrollment prefixes (`/api/v1/auth/passkeys/console/`, `/api/v1/auth/passkeys/enrollment/`), and the Console SPA (`/console/`). The plain HTTP listener serves only the subset in `INV-AUTH-ROUTE-02`; every other plain HTTP path redirects to HTTPS.
2. **mTLS-only routes (`RouteAuthMTLS`)**: Require a verified client certificate. Includes privileged PKI CSR signing (`/api/v1/pki/csr/sign`), producer endpoints (`/api/v1/observe/producer/*`), operator internal controls (`/api/v1/operators/validate`, `/target`, `/commands`, `/intents`, `/stop`, `/session/`), CLI rotation (`/api/v1/auth/cli/rotate`), CLISession refresh (`/api/v1/auth/cli/refresh`), CLI bind/unbind (`/api/v1/auth/cli/bind`, `/unbind`), CLI logout (`/api/v1/auth/cli/logout`), CLISession info (`/api/v1/auth/cli/session`), and CLI recovery approval via mTLS (`/api/v1/auth/cli/recovery/approve-cli`).
3. **Browser-session routes (`RouteAuthWebSession`)**: Validate the `ztd_web_session_cookie` against the persisted WebSession record. The user ID comes from the record and the WebSession ID is the cookie value (`INV-AUTH-ID-06`). Includes user profiles (`/api/v1/users/`), session introspection (`/api/v1/auth/sessions/`), browser transaction approvals (`/api/v1/approvals/`), browser passkey management (`/api/v1/auth/passkeys/`), read-only observe API (`/api/v1/observe/`, excluding the producer paths), and browser CLI recovery approval (`/api/v1/auth/cli/recovery/approve`). Under the web-session prefixes, `/api/v1/approvals/pending` and `/api/v1/auth/passkeys/cli/status` are mTLS-only exceptions.
4. **Dual-auth routes (`RouteAuthDual`)**: Try mTLS first and otherwise validate the browser-session cookie. mTLS is preferred when a certificate is present. Includes SSE streams (`/api/v1/sse/stream`, `/api/v1/sse/events`), operator list and binding (`/api/v1/operators`, `/bind`, `/unbind`, `/{id}/`), owner audit logs (`/api/v1/audit/events`, `/summary`, `/verify`, `/consensus-votes`), direct transaction approval and denial (`/api/v1/approvals/respond`), platform enrollment owner review and consensus binding (`/api/v1/auth/platform-enrollments/{pending,enrolled,decision,decisions,revoke,consensus}`), and OpenAPI documentation (`/swagger/doc.json`).
5. **Unknown HTTPS routes**: Default to mTLS authentication as a fail-closed rule.

## WebAuthn Passkey Authentication

The Console uses WebAuthn passkeys for passwordless authentication, human-presence attestation, and L3 Notary approvals:

- **Authenticators**: Platform authenticators (Windows Hello, Apple Touch ID / Face ID), roaming security keys (FIDO2 / YubiKey), and synced passkeys satisfy the ceremony.
- **User Verification**: Mandatory (`VerificationRequired`) across registration, login, and L3 passkey verification ceremonies.
- **Clone Detection**: The Gateway maintains the sign counter and timestamp. If an authenticator reports a non-increasing counter (`CloneWarning`), the assertion is rejected with `ErrPasskeyCloneDetected`.
- **Lockout Prevention**: Attempting to revoke the user's sole remaining passkey fails with HTTP 409 Conflict (`ErrLastPasskeyRevoke`).
- **WebSession**: Successful passkey authentication issues a 24-hour WebSession (`WebSessionTTL = 24h`) and sets the `ztd_web_session_cookie` (HttpOnly, Secure, SameSite=Lax; SameSite=None when the request is cross-origin).

## Mutual TLS and SPIFFE Identity Binding

Every workload (CLI, Operator, App) connecting over mTLS presents an X.509 certificate signed by the Operator Intermediate CA with a SPIFFE URI SAN under the canonical `ztd.local` trust domain:

| Workload Type | SPIFFE ID Format | Description |
| :--- | :--- | :--- |
| **Governed Operator** | `spiffe://ztd.local/operator/<org>/<op>/<session>` | Outbound operator session identity |
| **CLI / Client** | `spiffe://ztd.local/cli/<user>/<cli_session>` | Local CLI session identity |
| **Application** | `spiffe://ztd.local/app/<application_id>` | Delegated app/agent workload identity |
| **User Principal** | `spiffe://ztd.local/user/<user_id>` | Human user principal identity |
| **Gateway Hub** | `spiffe://ztd.local/hub/operator-listen` | Gateway listener serving identity |
| **Gateway Peer** | `spiffe://ztd.local/gateway/<gateway_id>` | Peer-to-peer federated gateway identity |

CLI and application leaf certificates have a 7-day validity (`leafCertValidityDays` in `internal/services/gateway/gateway_certs.go`, derived from `constants.MaxWorkloadLeafCertTTL`). Operator leaf certificates default to 7 days and may be shortened with `OperatorLeafCertTTL`; the enforced range is greater than zero and at most 7 days (`constants.MaxWorkloadLeafCertTTL`), and values outside it fail closed: config load and Gateway PKI construction both return `ErrConfigLeafCertTTLInvalid`, so Gateway startup fails. Operator leaves are renewed in-band over the `renewal:` pub/sub channel when the leaf reaches two-thirds of its lifetime (see [Operator Architecture](operator.md#in-band-certificate-renewal-over-mtls-pubsub)). Revocation is checked on every mTLS request, and the CRL is published at `/.well-known/ztd/pki/crl`.

## CLI Enrollment, Signatures, and Lifecycle

The `ztd login` and `ztd auth enroll user` commands manage the CLI identity state machine:

| Local and Gateway State | Action |
| :--- | :--- |
| No local identity and no gateway user | Bootstrap first owner and issue CLI identity |
| No local identity on initialized gateway | Request human-approved recovery via Console or `ztd auth approve-recovery` |
| Valid cert, matching gateway root, active session | Idempotent reuse; no new cert issued |
| Valid cert expiring within 24 hours | Rotate certificate via authenticated mTLS (`/api/v1/auth/cli/rotate`) |
| Valid cert but expired server-side session | Refresh session via `ztd auth refresh` (`/api/v1/auth/cli/refresh`) |
| Expired cert or mismatched gateway root | Recover identity or bootstrap if gateway is uninitialized |

- **Local Private Key**: Generated locally via ECDSA P-256 and never transmitted over the wire.
- **Refresh Flow**: `ztd auth refresh` uses the still-valid certificate as proof of identity to extend the certificate's own CLISession in place: the same session ID, the same certificate binding, a new expiry, and the operator binding re-resolved (`INV-AUTH-SESSION-08`, `INV-AUTH-OP-BIND-04`).
- **Logout Flow**: `ztd logout` calls `POST /api/v1/auth/cli/logout` over mTLS. The Gateway terminates WebSessions and CLISessions, unbinds operators, and revokes CLI certificates. Local credentials are deleted only after Gateway confirmation (or immediately via `--local-only`).
- **Transaction Approval**: `ztd auth approve <transaction-hash>` keeps the browser/WebAuthn flow as its default. `ztd auth approve <transaction-hash> --cli` unseals the enrolled CLI P-256 key in memory (`auth.LoadClientAuthContext`), signs the domain-separated transaction hash (`governance.SignCLIApproval`), and posts only the signature (`cli_signature`, `approved: true`) to `POST /api/v1/approvals/respond` over the authenticated mTLS connection (the route is `RouteAuthDual`, but the approval branch rejects callers without a CLISession and mTLS peer certificate). The Gateway takes the leaf certificate and its chain hints from that connection, never from the request body, builds the protobuf `L3Proof` (DER, SHA-256 fingerprint, intermediates, signature), and checks the certificate's CLI SPIFFE user/session identity and fingerprint against an active, non-revoked registered CLISession. The approving CLISession in that certificate may differ from the submitter CLISession bound into the transaction; approval does not rewrite the hashed envelope. The command succeeds only when the returned receipt matches the requested hash, is `COMPLETED`, and reports L3 status `REQUIRED_VALID`. `ztd auth approve <transaction-hash> --deny` posts `approved: false` to the same route over the same mTLS connection; a deny carries no signature. Under `ratify` and `notary` the Gateway accepts a deny only from a caller grounded for that posture: a CLISession must present an mTLS peer certificate, and a WebSession must belong to a user with a registered passkey. A transaction with a recorded owner can be denied only by that user; a transaction with an empty recorded owner is not owner-checked. The executing Operator then signs the `L3_DENIED` rejection. The command succeeds only when the returned receipt matches the requested hash and carries rejection code `L3_DENIED`. `--deny` and `--cli` are mutually exclusive.
- **Outbound Transfer of Approval Proofs**: For a transaction whose target is an outbound Operator, approval does not end at the Gateway. After the Gateway checks (active user, registered CLISession and certificate revocation, or passkey assertion with counter/clone detection), the original CLI signature or WebAuthn assertion is forwarded to the Operator. For a passkey, the Gateway attaches `PasskeyVerificationContext` (`L3Proof.passkey_context`) from its registered credential and rejects any client-supplied context. The Operator then verifies the proof itself: a CLI leaf must chain to the Gateway CA the Operator already pins, with its canonical CLI SPIFFE user equal to `requestor_user_id`; a passkey assertion must verify against the forwarded credential key, RP ID, and origins. The Gateway signs no substitute attestation. See [Layer 3 (L3) Notary: Human Authorization](governance.md#layer-3-l3-notary-human-authorization) for the verification rules and the blocking dispatch that keeps the original request open for the approval.

## Session Token Handling and Operator Binding

### Operator Binding Architecture

CLI commands bind to OperatorSessions through explicit server-side mappings:

```text
CLI Certificate (SPIFFE URI SAN)
      │
      ▼
CLISession (cli_session_id)
      │
      ├─► Primary Binding: operator_session_id
      │
      └─► Multi-Operator Binding: bound_operator_session_ids (up to 5,000)
```

1. **Embedded Operator**: Deterministic ID `embedded-operator`. Anchors first-user bootstrap without an enrollment lease.
2. **Binding Mutation**: Managed via `ztd operator bind <operator-session-id>...` (`POST /api/v1/auth/cli/bind`). The Gateway validates that each target OperatorSession is active and owned by the calling user. A bind updates the bound operators of the caller's active CLISession in place, keeping its CLI session ID and certificate grounding (`INV-AUTH-OP-BIND-06`).
3. **Session Stamping**: The Gateway stamps the active operator identity from the persisted CLISession record, rejecting forged caller-supplied identity headers (`INV-AUTH-OP-BIND-03`).

## Platform Workload Enrollment

Workloads (Operators and applications) enroll via owner-approved workflows governed by the active posture (`constants.Posture`):

1. **Operator Enrollment**: Outbound Operators enroll exclusively over the bootstrap WebSocket (`/ws/operator/bootstrap`). On a single socket, the Operator sends a `request` frame (CSRs, system fingerprint, `token_hash`, runtime config), immediately sends `complete` with proof of possession, holds for owner approval, and receives a `bundle` frame with certificates, session identity, the Gateway's `Posture`, and each bound L2 consensus member's identity and Ed25519 public key (`OperatorL2Trust`).
2. **Application Enrollment (`PLATFORM_COMPONENT_KIND_APPLICATION`)**: Applications generate keys and CSRs locally, persist an opaque token (sealed, with the key, in the pending enrollment state), and submit to `POST /api/v1/auth/platform-enrollments/request`. The request expires in 30 minutes:
   - **Under `doctrine` and `consensus` (`!posture.RequiresL3()`)**: An authenticated owner CLI (`CLISession` over mTLS) approves its own app enrollment in-line during `ztd mcp agent run <agent>` or `ztd auth enroll app <name>` (`POST /api/v1/auth/platform-enrollments/decision`), with no passkey ceremony and no second command required.
   - **Under `ratify` and `notary` (`posture.RequiresL3()`)**: `PLATFORM_ENROLLMENT_DECIDE` and `PLATFORM_ENROLLMENT_REVOKE` remain L3-gated. Submitting a decision or revocation without an inline passkey proof suspends the `GovernanceEnvelope` via `mcp.GatewayService.SuspendGovernanceEnvelope` (`StoreSuspendedTransaction`) and returns HTTP `202 Accepted` (`status: "l3_required"`, `posture`, `tx_hash`, `approval_url` at `/api/v1/approve/<tx_hash>`, which redirects to the Console approval view, `expires_at`, `message`). In the CLI, `ztd mcp agent run` / `ztd auth enroll app` prints `posture.HumanApprovalReason()`, the approval URL, and the expiry, then holds `GET /api/v1/auth/platform-enrollments/status?token=...&wait=true` (woken event-driven via `EnrollmentsDecided` at the `DocumentStoreService.DecidePlatformEnrollments` commit boundary when `ResumeWithL3Proof` replays the envelope). In the Console (`ApprovalsView.tsx`), a `202 l3_required` response from `POST /api/v1/auth/platform-enrollments/decision` immediately triggers the WebAuthn passkey ceremony (`approveTransaction(tx_hash)`) in-line.
   - **Optional L2 Signing Key**: An application MAY submit `app.signing_public_key`, the hex encoding of a separate 32-byte Ed25519 public key, alongside `app.csr_pem`. The CSR MUST still use P-256. The Gateway returns `fingerprints.signing_key` as lowercase SHA-256 hex of the raw Ed25519 key. Owner decisions and the deterministic protobuf `PlatformEnrollmentCompletionTranscript` bind this fingerprint together with the transport CSR fingerprint. Completion MUST supply both `proofs.app` (the existing P-256 proof) and `proofs.signing_key` (an Ed25519 signature over SHA-256 of the same transcript, encoded as unpadded base64url). Missing or invalid possession proofs fail before issuance. The CLI approval display and Console show the signing fingerprint. Applications without this optional key enroll normally but cannot bind as consensus members.
   - **Follow-On Completion Mutations (`AuthorizedByDecision`)**: Once `PLATFORM_ENROLLMENT_DECIDE` commits, the follow-on completion mutations (`PLATFORM_ENROLLMENT_ISSUE`, `PLATFORM_ENROLLMENT_PERSIST_POLICY`, `PLATFORM_ENROLLMENT_CREATE_SESSION`) at `POST /api/v1/auth/platform-enrollments/complete` carry `_authorized_by_decision` (`ActionType.AuthorizedByDecision() == true`) and inherit authority from the committed decision (`governance.L3Required` is false). `HandlePersistPolicy` and `HandleCreateSession` strictly require and field-by-field match the committed issuance (`ErrPlatformEnrollmentIssuanceNotCommitted`, `ErrPlatformEnrollmentIssuanceMismatch`). `HandlePersistPolicy` registers the optional signing public key from that issuance in `trusted_signers`; it propagates write failures and completes registration on retry even if the app policy already exists. An active signing key MUST be revoked before replacement; a completed issuance retry cannot overwrite a different registered key.
3. **Consensus Binding (`PLATFORM_ENROLLMENT_BIND_CONSENSUS`)**: Enrolled `PLATFORM_COMPONENT_KIND_APPLICATION` identities with enabled Ed25519 signers are bound as the Gateway's K-of-N consensus member set (`constants.DocIDConsensusBinding` in `constants.CollectionConsensus`) via `POST /api/v1/auth/platform-enrollments/consensus`. The bind request names the primary `app_id`, the HTTPS `endpoint_url`, optional `member_app_ids`, optional `quorum`, and a required `provider` (`application` or `tribunal`; any other value, including empty, is rejected by `constants.ParseConsensusProvider`). A `tribunal` binding also carries `model_tag` and `model_digest`. This bootstrap action (`IsBootstrapAction() == true`) is exempt from L2 gating across all postures and remains L3-gated under `ratify` and `notary`.
4. **Revocation**: The owner revokes completed enrollments via `ztd auth enroll revoke <request-id>` (`PLATFORM_ENROLLMENT_REVOKE`, L3-gated under `ratify` and `notary`). The Gateway revokes certificates, removes the application's signing key and matching consensus binding, terminates OperatorSessions, and immediately disconnects corresponding WebSocket channels. Signing-key and binding cleanup failures propagate to the governed receipt.

The CLI generates the optional signing identity with `ztd auth enroll app <name> --signing-key`. The Ed25519 seed is sealed with the transport key and token in pending state. A resumed attempt retains its original instance ID and keys; requesting a signing key for a pending attempt that did not include one fails before sending a request. On completion, the seed is sealed at `Config.AppSigningKeyFile(name)` independently of the P-256 transport key. `auth.LoadAppSigningKey` unseals it for a local consumer; plaintext and malformed seeds fail closed. Applications that manage their own keys can use the same typed enrollment API and possession proofs directly.

Use `ztd consensus enroll app <primary-app> <https-endpoint>` to submit the governed binding, repeating `--member-app` for every member (the primary app included) and passing `--quorum` when more than one member is given, and `ztd consensus status` (with the global `--json` flag for machine-readable output) to read the bound consensus. Binding validates HTTPS locally and at the Gateway. Under ratify/notary, a suspended binding prints the posture reason, approval URL, transaction hash, and expiry; `--json` returns the typed suspension. Submission is not completion: approve the transaction and then inspect the binding with `status`. These commands use the existing owner authorization and L3 suspension path without polling.

The Tribunal consensus members are the ordinary enrolled applications `tribunal-axiom`, `tribunal-concord`, `tribunal-variance`, `tribunal-pragma`, and `tribunal-nemesis` (`constants.TribunalConsensusMemberAppIDs`). Each is enrolled with `ztd auth enroll app <name> --signing-key` and human-approved under the same posture rules as any application. `ztd consensus enroll tribunal --model <tag>` enrolls any member whose sealed key is missing locally, then binds the panel; `--quorum` takes 3 to 5 (default 3). A member's signing key is sealed under the enrolling host's `.ztd/pki/apps/`, so a `tribunal-*` application enrolled on another host cannot vote on this Gateway. The binding's `tribunal` provider is set by the same governed `PLATFORM_ENROLLMENT_BIND_CONSENSUS` action, and the vote flow is in [Consensus Architecture](consensus.md).

Enrollment authorization uses the authenticated local account ID and active-owner checks, without selecting on `User.Provider`. `TestPlatformEnrollment_CLISigningIdentityAndConsensusAcrossPostures` exercises the real CLI client with a JWT/JIT-shaped owner across all four postures, and rejects binding by a second account. This is provider-independent authorization coverage, not evidence of implemented Okta/OIDC sign-in. The existing JWT/JWKS verifier is distinct from a complete OIDC login flow. Future federation must map verified issuer/subject pairs to local accounts; it must not substitute IdP tokens or login MFA claims for workload keys or transaction-bound L3 proofs.

## Authorization and Governance Interlock

Authentication admits a principal to a route. Authorization determines whether that principal may execute a governed transaction through the five-layer pipeline:

| Layer | Enforcement | Responsibility |
| :--- | :--- | :--- |
| **L1 Doctrine** | Universal | Static heuristics, blacklist patterns, Gitleaks secrets signatures, OWASP CRS |
| **L2 Consensus** | Posture-gated (`RequiresL2()`) | K distinct affirmative Ed25519 signatures from bound consensus members over `<tx_hash>\|<decision>` |
| **L3 Notary** | Posture-gated (`governance.L3Required`) | WebAuthn assertion or enrolled CLI P-256 signature over transaction hash |
| **L4 Warden** | Universal | Nonce reservation, replay prevention, hash integrity, Merkle root, proof verification |
| **L5 Actuator** | Universal | JIT capability minting, payload rehydration, command dispatch, signed receipts |

Under `ratify` and `notary`, Gateway L3 accepts either a WebAuthn passkey assertion or the enrolled CLI certificate signature. The existing browser approval remains the default; `--cli` uses the current CLISession and its enrolled P-256 key. The CLI signature proof is mutually exclusive with WebAuthn fields. The Gateway verifies the signature and transaction hash, then anchors the certificate fingerprint and approver session against its registered CLISession state, including active-session and revocation checks. For an outbound Operator target the Gateway forwards that same proof and the Operator independently re-verifies it against its pinned Gateway CA (CLI) or the Gateway-forwarded registration context (passkey); the Gateway check never replaces the Operator's verification. Under `doctrine` and `consensus`, posture does not require L3 for mutations.

Denials are submitted via `POST /api/v1/approvals/respond` with `approved: false`. The Gateway resubmits the suspended envelope with `L3Metadata.denied` set; the executing runtime's L4 rejects it in every posture with `GOVERNANCE_REJECTION_CODE_L3_DENIED`, and its L5 signs the rejection receipt. The deny needs no approval proof because it can only stop execution, and `denied` is outside the transaction hash. The response and the `approval.completed` event both carry the signed receipt.

## Procedures

### Enrolling the First Owner CLI

```bash
# Headless enrollment
./ztd login

# Browser enrollment with passkey registration
./ztd login web
```

### Refreshing an Expired Session

```bash
./ztd auth refresh
```

### Binding Operators to CLI Session

Set `OPERATOR_SESSION_ID` to the operator session ID to bind before running the bind command below.

```bash
# List available operators
./ztd operator list

# Bind specific operator session
./ztd operator bind "$OPERATOR_SESSION_ID"
```

### Approving Pending Workloads

Set `REQUEST_ID` to the ID of the pending enrollment request to approve, as reviewed in the first command below.

```bash
# Review pending enrollment requests
./ztd auth enroll pending

# Approve workload request
./ztd auth enroll approve "$REQUEST_ID"
```

## Anti-patterns

- **Bypassing route classification**: Calling internal handlers directly instead of routing through the Gateway (`INV-AUTH-ROUTE-01`).
- **Trusting identity headers**: Accepting caller-supplied headers instead of extracting identity from the transport certificate SPIFFE SAN (`INV-AUTH-ID-01`).
- **Re-enrolling instead of refreshing**: Re-running enrollment when `ztd auth refresh` suffices for a valid certificate with an expired CLISession (`INV-AUTH-SESSION-04`).
- **Refreshing with an expired certificate**: Attempting `ztd auth refresh` with an expired certificate instead of running `ztd auth enroll user` (`INV-AUTH-SESSION-03`).
- **Minting a CLISession for an existing certificate**: Persisting a CLISession under an ID the certificate's URI SAN does not name, so every later request fails the SAN match (`INV-AUTH-ID-07`).
- **Trusting the CLI session header on Operator certificates**: Stamping `X-ZTD-CLI-Session-ID` into the context for a request authenticated by an Operator certificate (`INV-AUTH-OP-BIND-07`).
- **Modifying host PKI to bypass tests**: Mutating OS trust stores rather than using isolated test fixtures.
- **Unchecked last passkey revocation**: Allowing a user to delete their sole remaining passkey (`ErrLastPasskeyRevoke`).
