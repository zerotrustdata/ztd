# Console Architecture and Development Guide

## Purpose

The ztd Console is the platform's browser frontend. It is a React and TypeScript single-page application built from `console/` and embedded in the single static `ztd` binary; the Gateway serves it at `/console/` on its HTTPS port.

The console shares the Gateway's origin, communicating exclusively with the Gateway over HTTPS without CORS configuration, using a first-party `SameSite=Lax` session cookie. It does not call Operators or expose a standalone browser service.

The console covers core platform administrative operations:
- **Authentication**: First-owner passkey enrollment, passkey sign-in, and CLI-initiated passkey enrollment (`#enroll=1&token=…`).
- **Approvals**: L3 Notary approval of suspended transactions (`#approve=…`), CLI recovery approval (`#recovery=…`), and platform workload enrollment review (`#platform-enrollment=…`).
- **Operator Inventory**: List of Operators with type (`embedded` vs `remote`) and capabilities, deploy commands, session binding/unbinding, and remote Operator termination/stop. Liveness is rendered dynamically from the Gateway's `stale_at` calculation.
- **API Reference**: Native, browsable reference for the Gateway's OpenAPI 2.0 specification (`?view=api`).
- **Account**: User identity, registered passkeys, and passkey revocation.

## Invariants

Ids are stable. Append the next free number within each group; do not renumber.

### Console Operations (`INV-CONSOLE`)

| ID | Rule |
| --- | --- |
| INV-CONSOLE-01 | The console is served exclusively by the Gateway at `/console/` from the embedded `internal/services/gateway/console/static` build. Its source is `console/`; `make console-embed` builds and refreshes the embed, and `make console-embed-check` fails when it is stale. |
| INV-CONSOLE-02 | The console calls only Gateway routes classified `RouteAuthNone`, `RouteAuthWebSession`, or `RouteAuthDual` in `internal/services/gateway/gateway_auth.go`. The browser talks only to the Gateway. Route path strings live in `console/src/lib/paths.ts`. |
| INV-CONSOLE-03 | The console never sends user or web-session identity as routing input. The Gateway derives user and web session from the HttpOnly cookie. Operator bind and unbind requests name only `operator_ids`. |
| INV-CONSOLE-04 | Every request uses `credentials: 'include'`; the SSE stream uses `EventSource` with `withCredentials: true` and carries only the non-secret `since_id` cursor. |
| INV-CONSOLE-05 | Secret-bearing URL fragments (enrollment and recovery tokens) are read once and cleared with `history.replaceState` before the first render. A one-time token or deep-linked approval is attempted at most once per page load. |
| INV-CONSOLE-06 | The Gateway serves the console with a `Content-Security-Policy` of `'self'` for default, script, style, and connect sources, `object-src 'none'`, and `frame-ancestors 'none'`. The console uses no inline script and no `innerHTML`. |
| INV-CONSOLE-07 | Event type strings come from `console/src/generated/events.ts`, generated by `make constants-generate` from `protocol/constants/events.json`. Unknown event types are ignored. |

### Console Development (`INV-CONSOLE-DEV`)

| ID | Rule |
| --- | --- |
| INV-CONSOLE-DEV-01 | Gateway route strings live only in `src/lib/paths.ts`; event type strings come only from `src/generated/events.ts` through `src/lib/events.ts`. |
| INV-CONSOLE-DEV-02 | Wire-protocol logic (WebAuthn encoding, SSE normalization and reconnect, Operator liveness, fragment intents, OpenAPI reading) stays in pure modules under `src/lib/` with unit tests. Components hold presentation and wiring only. |
| INV-CONSOLE-DEV-03 | A change to `console/` ships with a refreshed embed (`make console-embed`) in the same commit; CI runs `make console-embed-check`. |
| INV-CONSOLE-DEV-04 | The console adds runtime dependencies only when the platform cannot reasonably do without them. Current runtime dependencies are `react` and `react-dom`. |

```text

  src/
    main.tsx              Reads URL-fragment intents, mounts providers and App
    App.tsx               Signed-out vs signed-in shell, navigation, views
    lib/                  Pure modules: paths, api (credentialed fetch), webauthn,
                          sse (normalize + GatewayStream), liveness, fragment,

                          approvals, toast

                          approvals (ApprovalsView, RecoveryCard), api (ApiView),
                          account (AccountView)
    components/           Shared UI components (modals, tables, buttons, banners)
    generated/events.ts   Generated by `make constants-generate`; do not edit
  tests/                  Component tests driving App against fake Gateway
```

## Trust Boundaries

The console is an untrusted presentation layer with zero cryptographic keys or standing authority:

- **Authentication**: Verified by the Gateway. WebAuthn ceremonies execute in the browser; the Gateway verifies assertions and issues an HttpOnly, Secure `ztd_web_session_cookie`.
- **Authority**: Resides in the Gateway's governance pipeline (L1-L3) and executing Operators (L4-L5). Every console action is an authenticated HTTP request evaluated by the Gateway's policy gates.

## Approvals and L3 Ceremony

The Approvals view handles human-in-the-loop decisions:

- `#approve=<tx_hash>`: Deep link that initiates a WebAuthn assertion ceremony over the suspended transaction hash. Successful assertion notifies the Gateway via `/api/v1/approvals/`.
- **Deny** on a suspended transaction posts `{approval_id, approved: false}` to `POST /api/v1/approvals/respond`. Denial does not prompt for a fresh WebAuthn assertion, but requires an authenticated caller; under `ratify` or `notary`, a web caller must have a registered passkey and a CLI caller must use mTLS. The Gateway resubmits the denial marker to the executing Operator; L4 rejects it, L5 signs the `L3_DENIED` receipt, and the Gateway returns and publishes that receipt. Approval itself requires a WebAuthn assertion through the verify route.
- `#recovery=<token>`: Reviews an operator or CLI recovery request (`POST /api/v1/auth/cli/recovery/approve`).
- `#platform-enrollment=<id>`: Owner review of pending workload enrollment requests (`POST /api/v1/auth/platform-enrollments/decision`).

## Operator Inventory and Binding

- **Binding**: Attaches an Operator to the browser's web session via `POST /api/v1/operators/bind` and `POST /api/v1/operators/unbind`. The Gateway updates the `bound_web_session_id` on the Operator document.
- **Remote Stop**: Calls `POST /api/v1/operators/{operator_id}/stop` over browser session auth.
- **Dynamic Liveness**: The Gateway supplies `stale_at` timestamps on each Operator record. The console derives liveness locally in `console/src/lib/liveness.ts`:
  $$\text{status} = \begin{cases} \text{active} & \text{if } \text{now} < \text{stale\_at} \\ \text{stale} & \text{if } \text{now} \ge \text{stale\_at} \end{cases}$$
  A single client timer arms for the earliest future `stale_at`, avoiding polling loops.

## Native API Reference View

The API view (`?view=api`) provides an in-browser reference for the Gateway's OpenAPI 2.0 specification:
- Fetches `GET /swagger/doc.json` using the authenticated session cookie (`RouteAuthDual`).
- Parses and renders operations grouped by tag, with interactive parameters, responses, and schema models.
- Operates under strict CSP (`'self'`) without loading external CDN scripts.

## Event Delivery and Liveness

The console opens a single SSE stream to `/api/v1/sse/stream`:
- Initial connection requests live events (`since_id=0`) and loads state over HTTP.
- Reconnections resume from the highest durable event ID with exponential backoff (1s to 30s + jitter).
- Ephemeral events (heartbeats and approval invalidations) carry ID 0 and trigger state refreshes without advancing the resume cursor.
- Heartbeats update `last_heartbeat_at` and `stale_at` in place.
- Approval invalidations (`ztd.v1.platform.approvals.changed`) trigger debounced re-listing of pending transactions and enrollments.

## Procedures

### Development Setup

```bash
cd console && npm ci
```

### Developing Against a Running Gateway

```bash
make console-embed && make build && ./ztd gw restart
```

### Running Tests

```bash
# Typecheck and lint
make console-lint

# Vitest unit and component tests
make console-test

# Gateway embedded build test
./ztd test unit --pkg ./internal/services/gateway/console
```

### Shipping Changes

1. Run `make console-embed` to build the frontend and update `internal/services/gateway/console/static/`.
2. Commit the updated static assets alongside source changes.
3. Verify with `make console-embed-check`.

## Anti-patterns

- **Direct edits to embedded assets**: Editing `internal/services/gateway/console/static/` directly instead of running `make console-embed` (`INV-CONSOLE-01`).
- **Hardcoding API paths**: Defining route strings outside `src/lib/paths.ts` (`INV-CONSOLE-DEV-01`).
- **Injecting inline scripts or `innerHTML`**: Violating CSP policies (`INV-CONSOLE-06`).
- **Polling for state changes**: Implementing periodic intervals instead of relying on SSE events (`INV-CONSOLE-04`).
- **Parsing wire protocols in UI components**: Bypassing pure modules in `src/lib/` (`INV-CONSOLE-DEV-02`).
